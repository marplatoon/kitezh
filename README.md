# Kitezh

Kitezh - P2P-сеть, вдохновлённая I2P, но на onion routing (полный туннель, не garlic). Задумана для использования в России - приоритет на устойчивость к DPI-блокировкам и низкую задержку, а не на максимальную анонимность любой ценой.

## ⚠️ Текущий статус: сети нет

Это дизайн-документ и roadmap проекта на самой ранней стадии. Ниже - честный список того, что есть, и того, что только запланировано.

### Реализовано
- [x] Генерация ключей с библиотекой flynn/noise
- [x] Handshake между двумя узлами
- [x] Шифрование
- [x] Базовая передача сообщений (p2p)
- [x] TCP+uTLS транспорт с маскировкой под браузерный TLS-фингерпринт
- [x] Accept-цикл на сервере не роняет процесс от левых подключений (не-протокольный трафик просто отбрасывается)
- [x] Персистентность статического keypair на диск
- [x] Однохоповый relay
- [x] Сквозное шифрование
- [x] Закрепление публичного ключа цели (pinning, флаг `-targetkey`)
- [x] Таймауты на релее (dial, CONNECT, idle)
- [x] Allow-list на релее (флаг -allow)
- [x] Цепочка из двух релеев (заданных вручную)
- [x] Локальная таблица пиров (`-relays`, строка `ip:порт ключ` на пира) и случайный выбор хопов цепочки (`-hops N`, по умолчанию 2): хопы разные, берутся через `crypto/rand`, адрес цели в выбор не попадает. Проверено локально на трёх релеях и цели
- [x] Ячейки фиксированного размера (1024 байта шифртекста) на всех линках, длина сообщения и тип команды не видны по размеру записи
- [x] Onion-слои: на каждый хоп своя гамма ChaCha20 без тегов, размер ячейки по пути не меняется, целостность проверяет адресат
- [x] Цепочка достраивается по одному хопу (EXTEND), хендшейк хопа Noise_NK: клиент не показывает хопу свой ключ, ключ хопа закреплён
- [x] Цель как последний хоп цепочки (`-mode listen`)
- [x] Keepalive: клиент раз в 20-40с шлёт цели пустую ячейку через всю цепочку, тихий чат не умирает по idle-таймауту релеев
- [x] Старый режим передачи (прямой чат и релей через CONNECT/DATA) удалён, остался один onion-режим
- [x] TCP-потоки поверх цепочки: до 64 на цепочку, номер потока в заголовке relay-ячейки. Цель сама решает, куда они ведут (`-forward`), клиент слушает локальный порт (`-local`). Проверено на майнкрафте
- [x] Flow control для потоков: окно 1024 ячеек (около 1 МБ) на поток, подтверждение SENDME каждые 128 ячеек. Запись в сокет вынесена в отдельную горутину, поэтому медленный поток не задерживает остальные. Проверено локально на двух хопах: 500 МБ за 9 секунд, параллельный медленный поток скорость не режет. Через реальный VPS пока не мерили

## Идея и trade-off'ы (дизайн, не реализация)

Приоритет на низкую задержку - осознанный компромисс:

- Релеи предполагаются географически в России, а не по всему миру, как в Tor/I2P - это должно снижать пинг, но потенциально облегчает корреляционные атаки для наблюдателя, контролирующего значительную часть сети внутри региона
- Число хопов планируется держать минимальным (~3)

Ни один из этих пунктов пока не протестирован и не реализован - это только план.

## Как запустить и проверить?

```bash
git clone https://github.com/marplatoon/kitezh
cd kitezh
go mod tidy
```

Чат между A и C через релеи. Четыре шага, по порядку:

```bash
# B (релей):
go run . -mode relay -addr :9000 -key ./keys/b.key

# C (релей):
go run . -mode relay -addr :9001 -key ./keys/c.key

# D (конечный узел): в логе строка "Публичный ключ: <hex>" - он нужен клиенту
go run . -mode listen -addr :9002 -key ./keys/d.key
```

Клиенту нужна таблица пиров: `relays.txt`, туда вписываются адреса релеев и их публичные ключи из лога (формат `ip:порт ключ`, по строке на пира, пример в `relays.example.txt`). Порядок строк не важен: хопы цепочки клиент выбирает из таблицы случайно, сколько - задаёт `-hops`

```bash
# A (клиент): -hops - сколько случайных релеев из таблицы взять (по умолчанию 2),
# -targetkey - ключ D из его лога
go run . -mode dial -relays relays.txt -hops 2 -addr 127.0.0.1:9002 -key ./keys/a.key -targetkey <hex ключа D>
```

Режим потоков: цели добавляется `-forward 127.0.0.1:8080` (куда вести), клиенту - `-local 127.0.0.1:1080` (локальный порт). `curl http://127.0.0.1:1080/` на клиенте попадёт в сервис на цели. Привязывать `-local` стоит только к `127.0.0.1`

Цепочка подлиннее - больше `-hops` и достаточно строк в `relays.txt`. Если подходящих пиров меньше, чем `-hops`, клиент выходит с ошибкой, а не строит цепочку покороче. Адрес цели из выбора исключается, так что его можно держать в той же таблице

Что напишешь в A, появится в C, и наоборот. Ключи создаются сами при первом запуске, у каждого узла свой `-key`. Файлы ключей не коммитить.

## Дисклеймер

Хобби-проект. Делается в процессе обучения Go/сетям - не production-ready решение, не используйте это для реальной защиты от слежки, пока не появится хотя бы работающий прототип.

Для релейщиков ваще отдельное предупреждение. Прошу вас, учтите что ВСЮ ответственность за траффик, проходящего через вас, несёте только вы.
